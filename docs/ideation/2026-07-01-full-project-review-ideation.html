GroundingCodebase Context

Origin. web-temple is a BMAD-planned rebuild of florencetemple.org for Temple B'nai Israel (a small congregation in Florence, AL). It replaces a scattered set of tools with one server-rendered site: a Rabbi-controlled CMS, restored donations, a unified streaming surface, a member directory, live chat, and an events calendar. The stack is deliberate and constrained — Express 4 + EJS SSR multi-page app on Node ≥18, Postgres via pg, Redis (ioredis/Bull) for caching and the email/reminder workers, ws for live chat. No TypeScript, no bundler, no frontend framework, no inline <script>/<style> (strict CSP). Auth is a JWT in an httpOnly cookie decoded globally; CSRF is global via csurf.

Current state. Epics 1–4 shipped plus the Rabbi/Admin dashboard; ~12.6k lines of src behind ~1,183 passing tests. The July-2026 MVP tracks (member directory, donations, announcements, calendar, dashboard glue, launch readiness) are nearly complete. Everything is local-only on dev; nothing is pushed. Donations run on an intentional MockPaymentProvider because the Board authorizes real PayPal credentials only after evaluating the MVP — so the demo moves no money by design.

How this review was grounded. Seven evidence passes: a live browser UI pass (21 fresh desktop + mobile screenshots on localhost:3000, capturing the just-merged left-sidebar nav and clickable calendar), axis-sharded code scouts (auth, donations, chat/stream/calendar, ops), the four prior June ideation docs, the 2026-06-21 QA/feedback handoff, and external research on the stack's 2025–26 security and nonprofit-UX landscape. Candidates were then adversarially verified against the live code before surviving.

Already fixed — not re-litigated here Verification confirmed these earlier concerns are resolved on dev, so they are absent from the ideas below by design: CSP-blocked flows (password reset, Rabbi tour, Quill editor), tokenized RFC-8058 unsubscribe, trust proxy, the create-admin.js rewrite, admin-dashboard latency, the WS-upgrade auth gap, the contact-form CSRF 403, chat reconnect jitter, and the streams-into-calendar merge (both getEventsInRange and the popup already carry stream links).
External signals worth holding in view
  • csurf was deprecated (Express, May 2025) with documented weaknesses; csrf-csrf / csrf-sync are the migration paths. No frame surfaced this as a top idea (large lift, still functioning) — logged as a watch item, not scoped below.
  • Non-applicable after version check: the ws DoS CVE-2024-37890 (repo is on ws 8.20.1, past the 8.17.1 fix) and EJS SSTI CVE-2023-29827 (ejs 3.1.10, templates are static). Neither is a live vector here.
  • OWASP third-party-gateway guidance maps directly onto the coming PayPal work; ADA web-accessibility suits rose ~20% in 2025, 64% against sub-$25M orgs, with donation/registration forms a common trigger.

I1

Build the provider-authoritative capture path now — sandbox, hardened mock, conformance suite

donationsConfidence 85%Complexity Medium

Description. "Deferred until the Board authorizes" quietly conflates two different gates: real-money go-live (genuinely Board-gated) and writing and testing the provider-authoritative path (server-side amount recompute, a signed webhook receiver over the raw body, transmission-id idempotency) — which needs only a free PayPal sandbox key. Today MockPaymentProvider.capture() reads its outcome from req.body and there is no webhook receiver anywhere. Harden the mock to decide success/failure server-side and deliver results via an internal signed callback into a real receiver; build PayPalProvider against sandbox; and freeze the port behind a shared conformance suite that both the mock (today) and PayPal (tomorrow) must pass — encoding the OWASP requirements as executable assertions. Go-live becomes PAYMENT_PROVIDER=paypal plus a credential swap, not a from-scratch security build under Board time pressure.

Basis · direct
direct: src/services/payments/index.js — "a real PayPalProvider would be added here … once the Board authorizes"; evidence-donations.md — "only MockPaymentProvider exists; no PayPalProvider stub; no webhook routes; no signature verification"; capture() reads outcome from req.body.
Rationale

The donation feature's entire value unlocks on one Board decision. If the capture path and webhook receiver are only designed after that yes, real money rides on unproven, uncovered code written under deadline. Building the OWASP-shaped path against sandbox now respects the intentional sequencing (the mock stays for the demo) while making go-live a swap.

Companion — honest MRR label

The dashboard's "Monthly recurring" sums one-time initial gifts flagged donation_type='recurring' — stated intent, not realized charges (the mock has no monthly-charge engine). Rename/caption it ("Pledged recurring / mo" vs realized) so the very screen the Board reads to make its call doesn't over-promise banked revenue.

Downsides

A sandbox integration is real work before any revenue exists; the conformance suite must be written to the OWASP spec, not to the mock's current shape, or it just ossifies today's behavior.

I2

Fail-closed boot preflight — an aviation MEL that refuses to dispatch on red config

ops-launchConfidence 88%Complexity Low

Description. Several launch-fatal misconfigurations fail silently at runtime rather than at boot: a committed placeholder JWT_SECRET, an unset APP_URL that puts localhost links in production emails, ssl:{rejectUnauthorized:false} disabling DB hostname verification, and a non-numeric FACEBOOK_PAGE_ID rendering blank video cards with nothing in the logs. Borrow aviation's Minimum-Equipment-List: a startup preflight that asserts each no-go item (secrets not placeholders, APP_URL set and non-localhost, TEMPLE_EIN present, FACEBOOK_PAGE_ID numeric, Postgres CA cert present) and refuses to boot in production, naming the failed check.

Basis · direct
direct: evidence-ops-launch.md — "if APP_URL unset in production, all email links point to localhost"; db.js:16 ssl rejectUnauthorized:false in production; committed .env JWT_SECRET=your_jwt_secret_key placeholder; QA feedback — non-numeric FACEBOOK_PAGE_ID silently blanks video cards.
Rationale

These are exactly the mistakes a single-operator cutover makes. Each silently ships broken links, blank pages, forgeable auth, or a MITM-able DB, and none surface in the 1,183-test suite. A ~30-line fail-closed guard converts a whole class of silent launch-day disasters into one loud boot-time stop that names what to fix.

Downsides

Must be production-only and carefully scoped, or it blocks legitimate dev/test boots; the check list needs an owner so it stays in sync with new required env vars.

I3

One temple-timezone datetime formatter — kill the per-view UTC/local drift

ui-qualityConfidence 90%Complexity Low–Medium

Description. The same Friday service renders 10:34 PM on the public calendar but 5:34 PM in the admin table — a clean five-hour gap — because the public view hardcodes timeZone:'UTC' while admin calls toLocaleString() with no timezone (server-local). Homepage, popup, emails, and JSON-LD each format independently. Introduce one server-side formatInTempleTz() bound to a stored TEMPLE_TIMEZONE (America/Chicago) and route every surface through it, deleting the ad-hoc UTC and bare-local calls so the whole class of cross-surface disagreement collapses to a single tested function.

Basis · direct
direct: src/views/calendar/index.ejs uses toLocaleTimeString(… timeZone:'UTC') vs src/views/admin/calendar/list.ejs toLocaleString('en-US',{…}) with no timezone; evidence-live-ui.md — "10:34 PM public vs 5:34 PM admin — a 5-hour rendering discrepancy."
Rationale

A congregation site that shows a service at two different times is a direct attendance-and-trust failure — a member could arrive five hours off. A single source of truth also pre-empts the identical bug in reminder emails and the deferred webcal feed before they ship it too.

Downsides

Requires auditing every existing format call site; DST handling must live in the formatter (America/Chicago is CST/CDT), so it needs real tests around the transition dates.

I5

An operator health panel that speaks Rabbi, not pg_dump

ops-launchConfidence 80%Complexity Medium

Description. The admin dashboard shows a non-technical admin a red "Backup Failure Detected … pg_dump | openssl" block, "Server uptime 4m", and "Last backup —", while Redis outages silently no-op the donation alert and drop queued email jobs with no operator signal at all. Replace raw internals with plain-language status ("Backups: not yet configured — here's how", "Live chat: OK", "Email sending: degraded") plus a next-step link, and surface Redis/email-queue degradation as an honest banner instead of a swallowed log line.

Basis · direct
direct: evidence-live-ui.md — "prominent red 'Backup Failure Detected … pg_dump | openssl' … raw pipeline internals shown to the admin persona"; evidence-ops-launch.md — "Redis down = silent degradation (email queue loses jobs); no circuit-breaker."
Rationale

Self-hosted at ~$1K/yr with a Rabbi as the operator, silent degradation and engineer-speak mean real failures — lost donation alerts, no backups, dropped emails — go unnoticed until they cause harm. A readable panel is much of the difference between a runnable and an unrunnable launch.

Downsides

"Plain-language status" needs honest severity mapping so it doesn't cry wolf or, worse, hide a real red; some states (backup health) require a signal the app doesn't currently collect.

I6

Versioned ciphertext envelope — a one-byte prefix that unlocks key rotation and AES-GCM

accounts-authConfidence 85%Complexity Medium

Description. Member PII ciphertext is stored as base64(IV_hex:ciphertext_hex) with no key or algorithm tag, so there is no rotation mechanism and a re-save under a changed key can NULL still-recoverable data. Change the envelope to carry a leading version segment (v1:base64(IV:ct)), treat unprefixed values as legacy, and have decrypt select key + algorithm by version from a tiny keyring of current + previous keys. That one backward-compatible decision makes three deferred moves cheap and lazy: rotate ENCRYPTION_KEY (both keys coexist, re-encrypt on next write), migrate AES-256-CBC → AES-GCM, and stop clobbering recoverable data — the same trick TLS/PGP/KMS use.

Basis · direct
direct: src/utils/encryptionHelper.js returns Buffer.from(`${iv}:${encrypted}`).toString('base64') with no version tag; evidence-accounts-auth.md — "no key-rotation mechanism … no algorithm/version field in ciphertext"; grounding STILL-OPEN — "re-save can NULL still-recoverable ciphertext."
Rationale

Adopt the tiny format change now, while the member table is small, and every later security move — rotating the key, fixing the NULL-on-decrypt clobber, upgrading to authenticated AES-GCM — becomes a lazy migration instead of a risky big-bang re-encrypt of addresses and children's birthdays.

Downsides

Touches the encryption path, which demands careful, well-tested change and a legacy-format read path retained indefinitely; a keyring adds a small amount of key-management surface.

I7

Delete the WebSocket query-string token fallback

live-engagementConfidence 92%Complexity Low

Description. The chat upgrade reads the JWT from the cookie or the query string, and the query-string branch leaks a full auth token into access logs, proxy history, and Referer headers. Browsers already send the httpOnly auth_token cookie on same-origin WS upgrades, and the real client uses the cookie — so the query fallback is redundant and exists only as a credential-exposure surface. Remove the branch and require the cookie: strictly safer, no loss of function.

Basis · direct
direct: src/services/chatSocketServer.js:253 — const token = cookies.auth_token || query.auth_token;; verified that live-chat.js never sends auth_token in the WS query (it relies on the cookie). Grounding STILL-OPEN — "WS token-via-query-string fallback leaks to logs/history."
Rationale

A JWT in a URL is the textbook credentials-in-logs leak, and this token also gates chat identity and moderator status. Removing the branch is a pure-subtraction security win because the cookie path already delivers the token to the same handler.

Downsides

Essentially none for the shipped client; only matters if some non-browser/test client were relying on the query param — worth a quick grep before deleting.

I8

Transactional outbox for donation receipts & alerts — and a Redis-independent failure alert

donationsConfidence 78%Complexity Medium–High

Description. finalize() flips a donation to "completed" and writes its audit inside the DB call, but the receipt email, the 3-strike admin alert, and their delivery all fire from the controller after finalize returns — and the Bull jobs don't persist, so a crash or Redis outage in that window leaves a completed gift with no receipt and no alert. Banks never emit a statement outside the committed ledger transaction. Port the transactional-outbox pattern: within the same transaction that commits the state change, insert an outbox row describing the side-effect; a separate poller drains it with at-least-once idempotent delivery. As a companion, when Redis is down the 3-strike failure counter should fall back to a COUNT over the already-persisted failure rows so the alert still fires instead of resetting every request.

Basis · reasoned + direct
reasoned: transactional-outbox (Debezium / microservices messaging) writes state + intent atomically and drains async with idempotent retry. direct: evidence-donations.md — "lines 114-122 run outside the transaction … donation is completed but receipt/alert emails are lost"; the Redis-down alert path resets the counter each request; evidence-ops-launch.md — "Bull jobs don't persist; pending emails lost until restart."
Rationale

One pattern closes both the lost-receipt-on-crash gap and the Redis-down alert hole, and it is exactly the at-least-once reliability the real PayPal capture will require — so it's on the critical path to real money, not throwaway MVP scaffolding. A tax receipt's durability stops depending on a disposable cache.

Downsides

The heaviest survivor: a new table, a poller lifecycle, and idempotency keys. At current volume the simpler half (the Redis-independent alert fallback) may be worth shipping first, with the full outbox landing alongside the PayPal work.

I11

A production-parity "CSRF-on" critical-path test lane

ops-launchConfidence 85%Complexity Low–Medium

Description. NODE_ENV=test short-circuits CSRF globally (if (NODE_ENV==='test') return next()) — load-bearing, and it must stay — but it created a permanent blind spot where client-side _csrf token-wiring regressions are invisible to all 1,183 tests, and the same bug class has shipped at least three times (contact-form 403, admin Retry button, page-editor Save/Publish). Keep the global bypass, but add a thin dedicated Jest lane that boots with CSRF enforced and drives the real mint-token-then-submit flow for the highest-value forms (contact, donation checkout, admin writes). Bypass by default; exercise the real path deliberately.

Basis · direct
direct: evidence-ops-launch.md — "NODE_ENV=test skips CSRF entirely (server.js) … integration tests never catch CSRF failures"; QA feedback — "CSRF token missing on admin Retry button" and "Pages/CMS editor writes returned 403."
Rationale

CSRF-token regressions have shipped three times precisely because the suite is blind to them. A small CSRF-on lane makes that whole class visible in CI going forward — compounding across every future form the team adds — without removing the required test hatch.

Downsides

A second boot configuration to maintain; must stay scoped to a few high-value forms or it slows CI and duplicates coverage.

I12

Make single-process an enforced, declared invariant (boot advisory lock)

ops-launchConfidence 82%Complexity Low–Medium

Description. The codebase assumes single-process everywhere — 7 in-memory rate limiters, a per-process WS 50-connection cap, and email/reminder workers started unconditionally — yet nothing enforces it, so a routine second deploy silently N-times's the rate limits and races the hourly reminder scan. For a $1K/yr self-hosted single box, single-process is a legitimate choice; make it explicit with a boot-time Postgres advisory lock that refuses a second web+worker, plus a one-line documented invariant. This is the deliberate opposite lane to externalizing state, and it turns today's silent failure mode into a loud, guarded one.

Basis · direct
direct: evidence-ops-launch.md — "7 in-memory rate-limit stores … won't work multi-process"; reminder worker "no single-runner guard; N instances = N reminder scans racing at the hour boundary"; src/server.js workers "started unconditionally."
Rationale

It forces a lane choice — the code is either honestly single-process (guarded) or it externalizes state — instead of today's unhappy middle where corrupted rate limits and doubled worker load are completely silent to the operator.

Downsides

An advisory lock is a deliberate scaling ceiling; if the temple ever needs two instances, this is the thing that must be revisited first (which is the point — it makes that explicit).

I13

Honor the post-login redirect — and validate it as same-origin

accounts-authConfidence 88%Complexity Low

Description. requireAuth bounces unauthenticated deep-links to /login?redirect=<originalUrl>, but login.js ignores the param and hardcodes window.location.href='/' on success — so a member trying to reach a members-only page logs in and lands on the homepage instead. Read the redirect param, validate it as a same-origin relative path (closing the noted unvalidated-redirect concern), and default to a member landing area rather than the public homepage.

Basis · direct
direct: public/js/login.js — window.location.href = "/" on success ignores the param built at src/middleware/requireAuth.js:33 (res.redirect("/login?redirect=" + encodeURIComponent(req.originalUrl))); grounding STILL-OPEN — "unvalidated ?redirect= in requireAuth."
Rationale

Deep-link-then-login is the core members-only flow (directory, member archive). Dumping every login on the homepage makes the site feel like it forgot what you were doing — and wiring the redirect without validation would open an open-redirect. This fixes the friction and the latent security note together.

Downsides

The validation must be strict (reject absolute URLs, protocol-relative //host, and non-path values) — the whole security value is in getting that allowlist right.

I14

Error taxonomy: an AppError hierarchy plus one serialization middleware

ops-launchConfidence 78%Complexity Medium

Description. Services throw new Error('User not found') and controllers reply res.status(400).json({message: error.message}), so internal strings become HTTP bodies, and chat echoes raw err.message straight to clients. Introduce a small typed hierarchy (ValidationError→422, NotFoundError→404, AuthError→401/403, ProviderError→502, InternalError→500) plus one error-handling middleware that maps type→status and emits a safe client message while logging the detail. Once the convention exists, every current and future controller/chat/admin path inherits safe, consistent errors — and the PayPal work gets a ready-made ProviderError.

Basis · direct
direct: evidence-ops-launch.md — res.status(400).json({ message: error.message }) with services doing throw new Error("User not found"); evidence-chat-stream-calendar.md — "err.message sent directly to client. No sanitization."
Rationale

One choice converts a scattered class of leaks — auth internals, decryption-failure strings, chat echoes, even the pg_dump/openssl text surfaced to a non-technical admin — into a single tested mapping, and pre-equips the PayPal integration instead of re-inventing safe error handling per call site.

Downsides

Touches many call sites to realize the full benefit; landing it incrementally (middleware + the highest-leak paths first) avoids a big-bang refactor that competes with launch work.

I15

Shared EJS component kit with a traffic-signal action-color contract

ui-qualityConfidence 75%Complexity Medium

Description. The site has no shared component layer for interactive chrome, so it shows three different hero/page-header treatments, primary CTAs that flip gold/navy with no rule, raw native browser buttons for admin Delete/Feature with no danger styling, default-blue underlined links leaking into the footer and admin, and blank member cards with no empty-state. Build a small set of EJS partials — a page-header with one variant system, a button with an explicit semantic taxonomy (primary = gold, navigational = navy, destructive = red), and an empty-state partial — plus a CSS reset for native form controls, all in CSS with no inline styles. Color becomes a fixed contract (red = danger, never decoration) enforced by class, so a Delete can never render as an unstyled grey box.

Basis · direct
direct: evidence-live-ui.md — "row actions are raw native browser buttons … Delete has no visual danger treatment"; "three pages, three hero treatments"; "directory renders a completely blank member card … no fallback"; "primary CTA color flips between gold and navy with no discernible rule."
Rationale

The visual-consistency findings are all symptoms of one missing abstraction. A handful of partials plus a semantic color contract makes the CTA-color rule, the destructive-action affordance, and empty states enforceable in one place and free on every future admin/public screen — where the app is still actively growing new CRUD. It's the systemic version of I9 and I10.

Downsides

Lower-confidence because it's the largest surface-area change with the softest single failure; best sequenced as the substrate under I10 (donation form) and the admin tables rather than a standalone refactor.
